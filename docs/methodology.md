# 口径与算法

这份文档解释**每个数字是怎么算出来的**。如果你发现结果和手算不一致，先来这里对一遍；对完还是不对，欢迎开 issue。

---

## 0. 三条总原则

1. **只走确定路径。** 每个目标必须能回答「需要 N 个中间道具」，且 N 是公告写死的档位或保底次数。答不上来的（纯概率掉落、0.005% 开盒出将）不进方案，只在「获取路径」弹窗里灰显。
2. **不拿概率当货币。** 不给「平均 X 元能出」这种数。要么确定，要么标「均值」并明确写着它不可精测。
3. **保守优先。** 拿不准的取值就往「对玩家不利」的方向取。比如祈福按 1 灯 = 1 结（实际档位会额外返结，白赚），档位返利按券后消费判定（券减掉的部分不算消费，比按原价算更难达标）。

---

## 1. 第一层：目标 → 中间道具

每个目标在数据里挂着一到多个「系统」（`js/data.js` 的 `systems`），每个系统定义了一种换算：

| 系统类型 | 换算规则 | 例子 |
|---|---|---|
| `box` 礼盒 | 每开 **50 盒**返 1 传世宝玉（保底），所以 20 玉 = 1,000 盒 | 威曹彰 20 玉 → 1,000 盒 |
| `qifu` 祈福 | **1 灯 = 1 结**（固定口径），200 结 = 200 灯 | 任婉 200 结 → 200 灯 |
| `progress` 进度 | 累计到档位即领 | 谋钟会 120 令 |
| `gacha` 夺宝 | 吉运满 100 抽必得（保底档） | 夺宝皮肤 100 抽 |
| `jinxiu` 锦绣 | 绸缎兑换 + 累计寻觅档位 | 春宵彩翼 192 绸缎 |
| 直售 / 消费 | 直接标价，或「累计消费 N 元宝送」 | 直售皮肤 40 款 |

**白送的部分先扣掉**：登录福利、任务、钜惠勋章给的灯/令/夺宝券/锦绣都记在 `freeGains` 里，先从需求里减掉，再算要买多少。

> 例：任婉要 200 灯，活动白送 17 盏 → 实际只需买 183 盏。

---

## 2. 第二层：中间道具 → 元宝

同一个道具往往有好几种买法，引擎会把它们都列出来，取便宜的：

1. **系统商店**（`systems[].buys`）：单抽 / 十连 / 礼包，各有单价和限购
2. **商城礼包**（`extraPacks`）：跨系统的组合包，可能比单买便宜，但有购买次数上限
3. **直售**（`directSales`）：一口价
4. **单买兜底**（`singles`）：祈福灯 1,000 元宝/盏、传世宝玉 10,000 元宝/个

组合包还要过一遍 `comboSweep`：比如「纳贤组合礼包」一次给灯 + 令 + 锦绣 + 夺宝券，只有当这几样你都缺的时候才划算，引擎会判断该买几个。

**单买只算「需要买的那部分」**：任婉要 200 灯、白送 17 盏，单买按 183 盏计价，不会把送的再算一遍钱。玉同理，1 玉 = 50 盒折。

---

## 3. 第三层：元宝 → 人民币

这层最绕，因为它自己咬自己：**你花多少元宝，决定了你能领哪些每日档位奖励；而档位奖励又会返道具，减少你要买的东西。**

### 3.1 每日消费档位

每天消费达标可以领一档，档位累计：

| 消费 | 返 |
|---:|---|
| 1,111 | 抵价券1111 |
| 3,888 | 夺宝券×5 + 纳贤令×1 |
| 8,888 | 夺宝券×10 + 锦绣×2 + 券1111 |
| 18,888 | 纳贤令×5 + 券1111×2 |
| 28,888 | 纳贤令×10 + 券2888 |
| 38,888 | 祈福灯×1 + 夺宝券×50 |
| 58,888 | 纳贤令×10 + 券2888×2 |
| 88,888 | 纳贤武将自选福袋（只对指定 5 将有用） |

于是排程不是「摊平」或「集中」二选一，而是要枚举**消费摊在几天、每天冲到哪一档**。引擎枚举「活跃天数 1..9」，每个方案再算当天该冲到哪个档位最划算，取净支出最低的。

### 3.2 迭代到自洽

档位返的纳贤令、夺宝券会回冲需求，所以：

```
for round in 1..4:
    need = 总需求 − 期初 − 白送 − 上一轮档位返 − 上一轮充值返
    买 need → 排程 → 算这一轮实际能领多少档位返
    如果返利和上一轮一致，就收敛
```

四轮基本都收敛了。这也是为什么**券后数字偏乐观**的根源：它假设你能把档位返的券和道具全部用掉、且正好卡在门槛上。真实操作里差一点就领不到，所以右栏的「核对」表才是最终依据。

### 3.2.1 中间产物必须闭环，不能只记账

这套模型里「中间产物」有四种：每日档位返的券、充值档位返的券、充值档位返的道具、抵价券抵扣出来的实付。

每种都只有两种命运：**回冲需求** 或 **压低实付**。写在核对表里但不参与算式，报价就一定偏高——这是最容易犯、也最难一眼看出来的错误。

闭环规则：

| 产物 | 去处 | 不闭环的后果 |
|---|---|---|
| 充值返的灯 / 令 / 锦绣 / 券 | `need` 直接扣减（少买） | 充值送 97 令，方案照买 292 令，多花 ¥730 |
| 充值返的券 | 进券池，压当日实付（少充） | 券写在账本上，一分钱没省下来 |
| 每日档位返的道具 | `need` 扣减（下一轮） | 同上 |
| 每日档位返的券 | 进券池（同一轮内 `settle` 处理） | 同上 |

迭代用**只减不增**：下一轮假设取 `min(上一轮假设, 本轮实际)`。这样假设永远不超过实际，核对表不可能靠假设凑数；收敛后还要再验一次 `假设 ≤ 实际`，不满足就回退到更保守的那一轮。

判定「这笔返利对当单值多少」，用的是**当期商城最低可得价**（与倍率页同源），不是单买标价。用最低价折算偏保守：真买的时候往往比最低价贵，所以回冲的金额不会高估。

### 3.2.2 双倍箱只能选一条路

128 / 328 / 648 三档公告写的是「道具包 **或** 绑定元宝」，二选一。两条路线：

```
A（道具包）：到账 = 面额，返 N 盏灯 + M 颗球 + K 张券
B（换绑元）：到账 = 面额 × 2，不返道具
```

旧版本把两条加在一起算（到账翻倍 + 还拿道具包），¥128 档倍率虚高到 3.67×，连带把方案报价压低。

现在逐档先定路线再凑额，判据是「返的道具对当单值多少钱」vs「绑元面值」，取高的那条：

```
giveVal = Σ(道具量 × 当期最低可得价)，只算这单确实要的品类，券不算（券已经在 settle 里压过实付）
选 A ⇔ giveVal > altBind
```

券不参与这个比较，是因为它的价值已经通过「压低实付 → 少充钱」体现过一次，再算一次就是双重受益。

### 3.2.3 每日重置的档必须按天结算

一批档位写着「**每日重置**」，意思是每天各算一次，不是整期一次：

| 公告写法 | 判定口径 |
| --- | --- |
| 每日消费达到 X 元宝 | 当天**实付**（券后）≥ X |
| 每日重置，累计充值 X 元宝 | 当天**充值额** ≥ X，和单笔充值档**叠加** |

第三条最容易搞错。它不是「花 X 元宝买这个档」，而是「当天充够 X 就送」。充 60 元（6,000 元宝）那天：

```
6,000 元宝档 → 纳贤令 ×6
5,888 累计门槛 → 纳贤令 ×10   ← 这一份是白送的，不需要额外掏钱
─────────────────────────
一天 16 个令
```

旧口径把 5,888 塞进 `chargeTiers` 当独立档，等于要求额外再掏 58.88 元买那 10 令。初冬 5 天因此少算 40 多个令，这是 ¥346 的主要来源。现在单列 `P.dailyCumCharge`，在 `chargePlan` 里按天汇总充值额判定。

### 3.2.4 逐日预算：钱要摊到天，不能堆在最后一天

旧版 `distribute` 的目标是「把货铺到花钱最少的那天」，结果 11.16 期星曹仁 5 天里前 4 天各花 700，第 5 天一口气花 50,252。货全堆在最后一天，每日重置档只能吃一份。

现在是**逐日预算装箱**（best-fit decreasing）：

```
每天一个桶，容量 = 预算
商品按价格降序，放进「塞得下且塞得最满」的那天
全都塞不下（单件就超预算）时退到最空的一天
```

预算候选不是拍脑袋定的：

1. **当期各档位门槛**（3,888 / 8,888 / 18,888 / …）—— 金额不大时，摊开后每天刚好跨档；
2. **总额 ÷ 活跃天数，向上取最近档** —— 金额大时（秋日 12.8 万 / 5 天）没有这一项，1 万的预算根本装不下，装箱会退化成堆叠，逐日预算就成了摆设。

选哪一组 `(活跃天数, 预算)` 不能只看净消费。摊到多天会多吃几份每日档，花得少不代表拿得多。评分是：

```
score = 净消费 − 档位返利折算价值
```

返利折算里，**夺宝券必须按「实际能换回多少」算**，不能按每券单价乘总量：券的产出是阶梯的，每池只能领一次首档，200 券换 5 令、再多 1,700 券也只多换 5 令。按单价乘会高估五倍，评分于是偏向「券多」的方案，钱反而多花。

### 3.2.5 夺宝券是中间产物，不打夺宝就作废

公告里夺宝券的出路是累计进度，而不是直接兑换：

```
累计参与夺宝 40 次（消耗 200 券）→ 纳贤令 ×5
```

而且**同一期常有多个独立转盘**（11.16 期是「初冬夺宝」和「夺宝特惠」），进度各自计算、互不影响，所以每池都能各领一次首档 —— 400 券 = 10 令。

方案层的处理：

1. 档位 / 充值返到的券先收集起来（不直接扣需求，目标通常不需求券）；
2. 对每个转盘，取「第一个能换到目标品类的档位」——更高档给的是宝箱 / 皮肤，折算不了；
3. 按「每券换回价值」从高到低分配券，券不够整档就不打，不做半档；
4. 换回来的令回冲需求，券在账本上同步扣减。

漏掉这条，整期返的券就是白返：11.16 期星曹仁日消费档返 425 张，旧版一张没用上。

### 3.3 抵价券

- 三种券：3000-1111、3000-2888、6666-6665
- **一单只能贴一张券，但一单可以买多件同一商品**
- 门槛看的是**当单总额 = 单价 × 件数**，不是单件价格
- 来源：每日档位 + 充值档位 + 累计充值/消费档（外层迭代）
- 结算时先上大面额券，再按「凑够门槛所需件数」把同一件商品拆成多单

> **踩过的坑**：0.8.0 之前这里判的是 `单件价格 ≥ 门槛`。纳贤令礼包 1,000 元宝一件，永远够不到 3,000 的门槛，整期的券只有 8,888 的折扣礼包那一单能用——11 张 2,500 券实测只用出去 1 张。
>
> 拆单也不是越细越好：12 个 1,000 元的令并成 1 单只省 2,500，拆成 4 单（每单 3 个 = 3,000 刚好过门槛）能省 10,000。

**守恒式**（自检断言之一）：

```
期初券 + 每日档位给 + 充值档位给 = 用掉的 + 结余的
```

结余的券**不算沉没**，默认拿去单买祈福灯：每张券买够门槛的整数盏，守恒式为

```
灯数 × 1,000 − 实付 = 券面额
```

（1111/2888 券配 3 盏 = 3,000 元宝起用；6665 券配 7 盏 = 7,000 元宝起用。）

### 3.4 充值组合

目标：**用最少的人民币覆盖元宝缺口**。1 元 = 100 元宝。

八个档位，各有次数上限：

| 档位 | 返利 | 次数 |
|---:|---|---|
| ¥6 | 小红包×3 | 1 |
| ¥12 | 券6665 | 仅首日 1 次 |
| ¥12 | 券1111×3 | 11/8 起 1 次 |
| ¥30 | 水晶球×1 + 灯×3 | 每日 1 次 |
| ¥60 | 水晶球×2 + 灯×6 | 每日 1 次 |
| ¥128 | 水晶球×4 + 灯×7 + 券2888 | 每日 1 次（或双倍箱换绑元） |
| ¥328 | 水晶球×11 + 灯×7 + 券2888×3 | 整期 2 次（11/8 重置） |
| ¥648 | 水晶球×22 + 灯×7 + 券2888×6 | 整期 2 次（11/8 重置） |

**水晶球是硬约束**：只有 ¥30 及以上的档位给，所以需要水晶球的目标（谋程普要 11 颗）必须走对应档位，先用 DP 单独解「买够球的最便宜组合」，剩下的元宝缺口再用普通 DP 补。

**累计档是第二层返利**，和单笔档、每日档**叠加**发放：

| 类型 | 判定依据 | 例（初冬期） |
|---|---|---|
| 累计充值 | 到账元宝总额 | 充到 12,800 → 券2500×2；充到 28,800 → 券2500×3 + 令×3 |
| 累计消费 | 券后净消费总额 | 初冬期只有空档，没有实物奖励 |
| 每日重置·累计充值 | 当天充值额，天天能领 | 充 5,888/天 → 特惠精选纳贤令×10（5 天 = 50 令） |
| 每日重置·消费 | 当天消费额，天天能领 | 消费 10,000/天 → 夺宝券×400 |

> **踩过的坑**：0.8.0 之前 `cumCharge` / `cumSpend` 只解析出来喂给界面展示，方案一次都没读，等于把整期最大的一笔返利丢掉；「每日重置，累计充值 X」还被 `cumRe` 当成一次性累计档，10 令/天缩水成整期 10 令。

> **还没做**：这些档位现在只能吃到「集中一天打满高档次」的解。手搓攻略的做法是「每天花 1 万滚 5 天」，靠每日重置的夺宝券循环放大——要建模得把购买量从「总量 DP」改成「逐日预算 DP」，见 issue 里的待办。

> 注意两个 ¥12 档价格相同但内容不同（首日送 6665 券、11/8 起送 3 张 1111 券），代码里按**档位索引**区分，不是按金额——早期按金额查会把它们认成同一档，导致「¥12+¥12」实际是第一档买两次（而它限购 1）。

## 4. 期初存货怎么抵

| 存货 | 抵扣方式 |
|---|---|
| 元宝 | 先从最终充值额里扣（`净支出 = max(0, 净支出 − 期初元宝)`） |
| 祈福灯 | 1:1 抵灯的需求 |
| 纳贤令 | 1:1 抵令的需求 |
| 传世宝玉 | **1 玉抵 50 盒**（存量玉不产生开盒返玉，所以是抵盒不是抵玉） |
| 抵价券 | 进券池，和活动给的券一起排 |

抵价券和玉这两条容易算重，自检里专门有断言卡着。

## 5. 充值倍率表的口径

倍率 = **合计价值 ÷ 本金**，其中「合计价值」= 到账元宝 + 返利道具折算价值。

折算单价取「当期商城最低可得价」，和方案里实际买入价同源（`RATES.unitTable()`）。用单买标价会把倍率算高：

| 道具 | 折算 | 为什么是这个价 |
|---|---|---|
| 祈福灯 | 370（当期礼包最低单价） | 单买标价 1,000，但你不会真按标价买 |
| 纳贤令 | 200（每日特惠首抽） | 同上 |
| 锦绣 | 296 | 同上 |
| 狂欢夺宝券 | 59.2 | 同上 |
| 狂欢水晶球 | 3,000 | 只能靠充值档送，商城无货 |
| 抵价券 | 面额 × 可用率（1111/2888 → 85%，6665 → 60%） | 越大的券越难凑门槛 |
| 绑定元宝 | 1:1 | 就是钱 |

### 双倍箱必须分开算

¥128 / ¥328 / ¥648 是「道具包 **或** 绑元」二选一。两条路线要分别算再取高的那条，**不能相加**：

| 档位 | 道具路线 | 绑元路线 |
|---|---|---|
| ¥128 | (12,800 + 17,047) ÷ 12,800 = 2.33× | 25,600 ÷ 12,800 = 2.00× |
| ¥648 | (64,800 + 83,321) ÷ 64,800 = 2.29× | 129,600 ÷ 64,800 = 2.00× |

早先的版本把两条加在一起（到账按绑元、返利又按道具包），三档倍率凭空高出约 1 倍。

### 三个倍率，差别只在「产出算不算数」

| 口径 | 计什么 | 什么时候看 |
|---|---|---|
| 拿 15-1 | 全部产出 | 目标既在 15 选 1 名单里，你也练纳贤 |
| 拿非 15-1 | 扣掉 15-1 类 | 目标不在名单里，但纳贤令还有用 |
| 不拿纳贤 | 再扣纳贤令 | 根本不练纳贤将 |
| 含消费 | 再加消费档位返利 | 想知道「钱花完之后还能返多少」 |

消费返利按「每天花到刚好够最高一档」估，天数不超过活动天数——档位是逐档累计的，摊平反而拿得少。

### 组合倍率

勾选多个档位时：

```
组合倍率 = Σ(各档合计价值) ÷ Σ(各档本金)
```

这是按本金**加权平均**，所以组合倍率必然落在参与档位的最低～最高之间——它不可能比最好的那档更高，也不可能比最差的那档更低。组合器的作用是回答「额度不够、只能几档拼着充时，整体还剩多少效率」，不是用来刷高倍率。

> 例：¥12（首日，4.33×）+ ¥6（1.00×）→ 本金 ¥18，合计价值 5,799，组合倍率 3.22×。

### 凑额 DP

给定「我要花掉 X 元宝」，求覆盖 X 的最省充值组合。三个口径各出一个解：最省（钱最少）、笔数最少、返利最多。

## 6. 最低消费反查

反向问题：给定要买的道具，**最少花多少钱能拿到**。

做法是枚举而不是猜：

```
枚举 消费活跃天数 act = 1..9
  └─ 固定天数后，枚举「每天冲到哪一档」的分布
       └─ 每个分布用凑额 DP 求最省充值组合
            └─ 计算实付、用掉的券、达标领到的档位奖励、剩余
```

三层枚举会爆，所以用**下界剪枝**：先算出「券前元宝 ÷ 最大倍率档位」作为理论下界，凡是当前组合的人民币已经超过已知最优解就直接剪掉。

输出 Top3：

- **最省**：人民币最低
- **省心**：天数摊满（每天定额，不用记哪天冲）
- **快出**：1 天集中（当天见分晓）

反查结果通常比主界面的券后价更低，因为它在排程结果之上又用凑额 DP 重算了一遍充值组合（多套档位组合择优）。**回归断言按主界面的口径**，两者不冲突。

## 8. 已知偏差

诚实列出来，用的时候心里有数：

1. **券后偏乐观**：迭代假设返的券和道具 100% 用得上、且正好卡门槛。靠返券滚起来的目标（夺宝系、纳贤系）偏差最大，最终以「核对」表为准。
2. **档位判定按券后**：真实规则里券减免的部分算不算消费，公告没说死，这里取保守假设。
3. **不建模通元转绑元**：公告没写规则，双倍箱一律按绑元计（保证「能花」）。
4. **样本集有限**：只有五个手工核过的基础目标做回归，没有真实充值流水。
5. **单买价是折算价不是售价**：玉 10,000 元宝/个是按 50 盒保底反推的，实际开盒有随机掉落，真实成本可能更低。
6. **逐日预算只对「装得下」的期次有效**：金额远超「天数 × 最高门槛」时（秋日 12.8 万 / 5 天），每天必然超档，装箱退化回均匀分摊，拿不到「每天刚好跨档」的收益。这种期次只能靠总量最优，不再有逐日红利。
7. **收敛是保守的，会多买**：外层迭代只接受「假设返利 ≤ 实际返利」且不缺料的解。真不动点附近往往不可兼得——假设调高就少买、少买就掉档位、掉档位就返不够，只好收在保守端。金秋预热因此多买约 30 个令（¥1,594 vs 旧解 ¥1,494，旧解依赖了被证伪的假设）。
8. **多重充值口径未验证**：手搓攻略里「充值 132 元、累计消费 21,000 元宝」在 1:100 的汇率下不成立，疑似游戏内有首充双倍或额外返利，公告没写。工具不猜，按公告口径算，因此报价会比这类攻略高。
