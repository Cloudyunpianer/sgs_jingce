## 二、这一轮修的 5 个问题

### 1. 表格单元格里的 markdown 加粗没清

官网转出的表头常写成 `| **登录天数** | **奖励1** |`，`cells()` 只做 trim，`**登录天数**` 不等于 `登录天数`，于是「需购买的勋章表」被判成「活跃任务白送」。

中秋期因此把 6888 / 13888 两枚勋章的产出（纳贤令 16、夺宝券 250、锦绣 39）全算成白送，总价虚低 207 元。

修：`cells()` 里去掉 `**`。改完 `freeGains` 为空、`boughtGains` 带 6888/13888 价格。

### 2. 签筒建了模型但没接进方案

`parser.js` 一直在解析签筒（16 个），`engine.js` 也有「不放回，最多抽 N 次必中」的 chain，但 `needOf()` 里没有 `kind === 'tube'` 分支 —— 于是靠签筒出的目标全部落进「本期无确定途径」，方案给 **¥0**。

中秋期三个目标（张琪瑛转生丹、阎象、周不疑）全中招：页面显示 ¥0，看起来像白送，其实是算不出来。

修：
- `parser.js` 给签筒系统补 `sign`（签种 = 签筒名去序号，价格从商城表按名字找）和 `buys`；
- `plan.js` 加 tube 分支：`签数 = N − prizes + 1`（不放回抽，筒内签数抽完必出大奖，**保底次数是确定的，不是概率**），成本 = 签数 × 签单价。

中秋期由 ¥0 → ¥3,000（金瑶签 1000 通用元宝 × 100 签 × 3 个目标），`noRoute` 清零。

### 3. 无渠道 / 无法报价被静默吞掉

- 目标没有购买渠道（`noRoute`）→ 之前只影响卡片文案，总价照给；
- 需求道具本期买不到（`unbuyable`，比如秋华没有礼盒）→ 之前界面完全不提示，只显示 ¥0。

修：`plan.js` 输出 `noRoute` / `priced`，`ui.js` 在「需要充值」处直接显示 **无法报价**，下方加黄色提示说明是「未计入报价」还是「本期买不到」，并把空状态文案从「白送够了」改成「无法报价」。

### 4. 券名写死三档

`ui.js` 的 `CN` / `COUPON_NAME` / `CPN_LBL` 只认 1111 / 2888 / 6665。新样本的券是 1000 / 1001 / 1500 / 1888 / 2500 / 2888 / 6666 / 3000，页面上会直接显示原始 key `券1888`。

修：`cpnLabel()` / `cpnShort()` 从 `P.coupons[k].face` 动态生成，显示「抵价券1888」。

### 5. 表格字段不竖直对齐

三处都改了：

**右栏每日方案（卡片）** 原来是 flex：日期宽度随「11月7日 / 11月10日」变化，充值内容长度也变，「消费」后面跟 `margin-left:auto` 把数字顶到右边 —— 每天的数字左边缘、标签位置都不一样。

改成 4 列 grid（`62px | 1fr | auto | 78px`），「消费」标签和金额拆成两个 grid item，空充值也占位。

**「每日方案表」弹窗** 原来是 5 列，充值档位是 `¥648 + ¥328 + ¥128 + …` 这种长串且右对齐，表头挤在右侧、内容从左边开始，看着就是错位。

改成 6 列：日期 / 充值档位（左对齐）/ **充值合计**（右对齐，新增）/ 当日消费 / 买到什么 / 当天领奖，并给表格加 `table-layout:fixed` 钉死前四列宽度。

**「全部精测表」/「充值倍率表」** 表头 `.num` 没有右对齐规则（只有 `td.num` 有），所以「元宝 / ≈元 / 返利折算 / 合计价值」这些表头一律左对齐、数据右对齐。

补 `.modal-body th.num,.plan-table th.num{text-align:right}`；倍率列的进度条从数字右边移到左边，数字右边缘才能对齐。

实测（`getBoundingClientRect`）：每日方案 9 天的日期、充值、标签、金额列坐标完全一致，长数字 300,000 和 0 同列右对齐。

## 二·补、中间产物链条体检（0.8.0）

「中间产物」指活动过程中产出的、能顶钱的东西：抵价券、每日档位返的灯/令/券、充值档位返的道具、双倍箱换来的绑元。它们只要有一条没接进算式，报价就是错的。

体检方式是把每期的账摊开，逐笔对四条链：

```
本金 → 充值档位 → 到账元宝 + 返利券 + 返利道具
                       ↓              ↓            ↓
                  能否覆盖消费     压当日实付    能否少买
                       ↓              ↓            ↓
                  重新算充值 ← 净消费 ← 购买清单（已扣返利）
```

四条链上各挂一个断言（都进了 `tools/check.js`）：到账够花、逐项不缺料、返利假设 ≤ 实际、双倍箱不叠加。

### 查出来的两处

**① 充值返的灯 / 令没有回冲需求（报价虚高）**

秋日期需要纳贤令 320 个。充值档位实际返 97 个，但方案仍按 292 个下单——返的 97 个只出现在「核对」表的「充值」列里，没有参与「要买多少」的算式。

```
秋日 09.14（3 目标，需求 320 令）
  白送 1 + 档位返 27 + 充值返 73（保守假设）+ 买 219 = 320
  修复前：买 292 → 消费 283,052 元宝 → ¥2,806
  修复后：买 219 → 消费 210,052 元宝 → ¥2,078   省 ¥728
```

**② 方案里的双倍箱在双算（报价虚低）**

`chargePlan` 给产出赋值时无条件累加档位道具，同时又按「换绑元」把到账按两倍算。结果是同一笔 ¥128 白拿了 25,600 绑元 **和** 4 球 + 7 灯 + 1 张券。

这一处比①更危险：它让报价看起来便宜，实际充进去的钱根本不够花。修法是把 A/B 两条路线分开，逐档先定路线再凑额。

| 目标 | 修复前 | 修复后 | 原因 |
| --- | ---: | ---: | --- |
| 威曹彰 | ¥768 | **¥840** | 双倍箱不再白送道具包 |
| 谋钟会 | ¥262 | **¥280** | 同上（可用券从 3 张变 1 张） |
| 任婉 | ¥614 | **¥646** | 同上 |
| 春宵彩翼\*任婉 | ¥280 | **¥310** | 同上 |

### 修完的样子

`node tools/check.js` 157 项全绿。每期方案都能通过四道闸：

| 期 | 到账元宝 | 净消费 | 逐项缺口 | 返利假设 |
| --- | ---: | ---: | --- | --- |
| 开学焕新 | 602,728 | 602,728 | 无 | 无回冲 |
| 秋日活动 | 207,800 | 207,552 | 无 | 令 73 ≤ 97 |
| 中秋砸蛋 | 300,000 | 300,000 | 无 | 无回冲 |
| 金秋预热 | 221,748 | 221,748 | 无 | 令 59 = 59 |
| 金秋盛典 | 597,840 | 597,840 | 无 | 无回冲 |

### 还剩两处保守

1. **返利假设天然滞后一轮**。秋日实际返 97 令，但「按 97 令少买」会让充值额下降、实际只返 73，所以最终只能按 73 算。多出来的 24 令要么放弃、要么多充 24,000 元宝去换——两者打平，不算损失。
2. **结余券不进报价**。秋日 25 张券 2500 只用掉 1 张：当期能上券且过 3,000 门槛的商品只有「纳贤折扣礼包」（限 1 次）。剩下的券只能拿去单买祈福灯兑现，而该期商城没有灯单卖，所以只在「结余券去处」里列出来，不折进报价。

## 四、仍然算不出来的

1. **砸蛋 / 连连看 / 绘卷 / 福喵 / 积惠特卖**：这五个是「花元宝换皮肤碎片/积分」的玩法，公告里没有稳定的保底进度表，只识别活动名并列进 `unsupported`。
2. **签筒的如意莲路线**：现在只算「抽满必中」的上限（100 签）。实际上抽签给的如意莲能在如意商城兑换大奖，可能更便宜。这条路要按莲的产出做期望，跟「不算概率」的口径冲突，暂不做。
3. **概率直出**：0.5% 开盒出武将这类，只灰显参考。
