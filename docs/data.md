# 数据维护与换期

活动换期后，先走「导入本期 md」——解析器现在能覆盖大部分板块。导入后仍有对不上的，再按这份文档手改 `js/data.js`。

---

## 数据都在 `js/data.js`

一个 `PRESET` 对象，顶层字段：

| 字段 | 内容 | 换期要改吗 |
|---|---|---|
| `meta` | 活动名、起止日期、天数、元宝汇率、公告来源 | 导入自动改 |
| `singles` | 单买兜底价（灯 1,000 / 玉 10,000） | 一般不变 |
| `params` | 未公示的假设参数（碎片比例、锦绣档位、吉运） | ⚠️ 看公告 |
| `systems` | 各商店 / 礼盒 / 祈福 / 纳贤 / 夺宝 / 锦绣的规则与单价 | 导入重建 |
| `shops` | 商店商品（祈福商城、锦绣商店等） | 导入重建 |
| `dailyTiers` | 每日消费档位 → 返什么 | 导入解析 |
| `cumSpend` | 累计消费档位 → 返什么 | 导入解析 |
| `coupons` | 抵价券面额与门槛（按面额动态生成 key） | 导入解析 |
| `chargeTiers` | 单笔充值档位 → 返什么 | 导入解析 |
| `cumCharge` | 累计充值档位（只做展示） | 导入解析 |
| `extraPacks` | 商城礼包（可跨系统） | 导入解析 |
| `consumeRewards` | 累计消费送武将 | ✅ 手改 |
| `freeGains` | 活跃任务真白送 | 导入解析 |
| `boughtGains` | 买了勋章才有的产出（带价格） | 导入解析 |
| `directSales` | 直售皮肤 | 导入解析 |
| `unsupported` | 本期有但没建模的玩法 | 导入解析 |

## 导入覆盖到哪一步

| 板块 | 识别依据 | 状态 |
|---|---|---|
| 珍宝礼盒 | 「稀世珍宝」段里 `道具 / 概率` 表 + 上方 `**XX礼盒**` | ✅ |
| 珍宝 / 如意 / 锦绣 / 水晶球商店 | 表头含「消耗宝玉 / 兑换所需 / 兑换价格 / 水晶球」 | ✅ |
| 纳贤进度 | `累计纳贤X*N，可领取奖励：` | ✅ |
| 夺宝转盘 | `累计参与XX夺宝N次（消耗XX夺宝券*M）` | ✅ 去专名 |
| 签筒 | 表头含「总签数」；签种名 = 签筒名去序号，价格从商城表同名列取 | ✅ 接进方案（保底 = 总签数 − 大奖数 + 1） |
| 祈福 | `祈福积分达到N，可领取奖励：…限完成1次` | ✅ |
| 皮肤直售 | `商品名称/皮肤名称 + 说明 + 售价`，上下文含「皮肤直售」 | ✅ |
| 限时商品 / 免单商城 | `商品名称 / 说明 / 售价` | ✅ |
| 单笔 / 累计充值 | `单笔充值N元宝，可领取奖励：…` / `累计充值达到N元宝，…` | ✅ |
| 每日 / 累计消费 | `每日消费达到N元宝，…` / `累计消费达到N元宝，…` | ✅ |
| 抵价券 | `抵价券（A-B）` | ✅ |
| 群英绘卷 / 砸蛋 / 连连看 / 福喵 / 积惠特卖 | 章节标题 | ⚠️ 只标记，不建模 |

> 品类归一在 `js/currency.js`：任何 `XX夺宝券 → 狂欢夺宝券`、`XX水晶球 → 狂欢水晶球`、`XX纳贤令 → 专属`。引擎侧的 key 名字带「狂欢」是历史包袱，不影响换期。

### 回归样本

`samples/` 里放着 5 期官网公告的 markdown 原文（09.05 开学焕新 ~ 10.01 金秋盛典），`tools/check.js` 每跑一次都会重新解析、建库、报价，比对天数 / 目标数 / 三目标总价。改完解析器如果这里的数字变了，说明解析行为改了，需要确认是有意为之。

要加新样本：把公告粘进页面「导入本期 md」跑通后，再把同一份 markdown 存进 `samples/`，并在 `tools/check.js` 的 `SAMPLES` 里补一行期望值。

## 仍需手改的部分

### 1. `consumeRewards` — 累计消费送武将

```js
consumeRewards: [
  { name: '谋程普', need: 111100, note: '个人热力 1111（每消费100元宝=1热力）' },
]
```

这类「消费到某个额度直接给武将」的路线，公告写法差异太大，解析器不碰。

### 2. 新玩法的建模

群英绘卷、幸运砸蛋、欢乐连连看、福喵纳财、积惠特卖这五种，只有活动名被识别。要算它们，得在 `data.js` 里加 system、在 `engine.js` 加对应 kind 的支路。

### 3. 内置期的口径

内置双十一数据用的是 0.4.0 的手工口径（勋章产出算白送、勋章价格未计入成本）。导入当期会自动切换成严格口径（勋章算「需购买」），两边数值会有差异。

## 附录：档位字段参考

### dailyTiers — 每日消费档位

```js
dailyTiers: [
  { need: 1111, gives: { 券1111: 1 }, note: '抵价券1111 + 凡木签×1' },
  { need: 3888, gives: { 狂欢夺宝券: 5, 纳贤令: 1 }, note: '夺宝券×5 + 纳贤令×1' },
  // ...
]
```

`need` 是当天消费门槛，`gives` 是返的道具（键名要和 `systems` 里的单位对得上）。排程引擎会枚举「摊几天、每天冲到哪档」，所以这张表直接决定结果。

### chargeTiers — 充值档位

```js
chargeTiers: [
  { need: 600, gives: {}, total: 1 },                                    // ¥6
  { need: 1200, gives: { 券6665: 1 }, onlyDay: 1 },                      // ¥12 仅首日
  { need: 1200, gives: { 券1111: 3 }, fromDay: 2, total: 1 },            // ¥12 11/8 起
  { need: 3000, gives: { 狂欢水晶球: 1, 祈福灯: 3 }, perDay: 1 },          // ¥30 每日
  { need: 32800, gives: { ... }, total: 2, alt: { 绑定元宝: 32800 } },     // ¥328 整期 2 次
]
```

次数用三个字段表达，注意别写重：

| 字段 | 含义 |
|---|---|
| `onlyDay` | 只在第 N 天可买 |
| `fromDay` | 第 N 天起可买 |
| `perDay` | 每天 N 次，总量 = N × 活动天数 |
| `total` | 整期总量（优先于 perDay） |
| `alt` | 双倍箱的另一个选项（换绑元） |

> **坑**：两档金额相同（比如两个 ¥12）时，代码靠**数组索引**区分，不是 `need`。如果你手改时把顺序打乱，组合器可能选错档——改完顺手跑一遍 `node tools/check.js`。

### extraPacks — 商城礼包

```js
{ id: 'up2', name: '狂欢升级礼(2)', price: 6888,
  gives: { 纳贤令: 5, 盒: 10, 狂欢夺宝券: 50 },
  total: 1, chain: 1, exclusive: '谋钟会' }
```

- `total` 限购次数，`perDay` 每日次数
- `chain` 表示「买齐前 N 个才能买」的递进礼包
- `exclusive` 表示只对某个武将有用

## `systems` 怎么加一个新目标

每个目标挂在若干个 system 上。以礼盒为例：

```js
{
  id: 'box_wcb', kind: 'box', name: '威曹彰礼盒',
  unit: '盒', pool: 'jade',
  buys: [
    { qty: 1,  price: 200 },     // 单盒 200 元宝
    { qty: 50, price: 9900 },    // 50 盒打包
  ],
  items: { '威曹彰': { jade: 20 } },   // 20 玉换
}
```

`kind` 决定换算方式（`box` / `qifu` / `progress` / `gacha` / `jinxiu`），`pool` 决定需求合并到哪个中间道具池。

新加一个武将，通常是：

1. 在对应 system 的 `items` 里加一行（多少玉 / 多少结 / 多少令）
2. 如果它有自己的礼盒，复制一个 system 块改 id 和单价
3. 跑 `node tools/check.js`，看四类覆盖还成不成立

## 导入后自查清单

1. 弹窗里「本期公告未找到」是否为空——空了说明核心板块都读到了
2. 「未纳入精算的玩法」是否和公告对得上
3. 目标列表里有没有明显不该出现的武将（说明上一期数据没清干净）
4. 随便点一个目标，看「核对表」的需求数是否符合公告写的次数
5. 跑 `node tools/check.js`，确认解析器没被改坏


导入后：

- 数据存 `localStorage`，刷新不丢
- 想回滚点「恢复内置」
- 清浏览器缓存 = 回到 `data.js` 的默认值

## 换期 checklist

```
[ ] 1. 改 meta（活动名、起止日期、天数）
[ ] 2. 跑「导入本期 md」，看识别结果
[ ] 3. 手改 dailyTiers（8 档门槛 + 返利）
[ ] 4. 手改 chargeTiers（档位、次数、双倍箱）
[ ] 5. 手改 extraPacks（礼包、限购、递进关系）
[ ] 6. 核对 systems 里的礼盒单价与兑换数
[ ] 7. 更新 freeGains（登录送什么）
[ ] 8. 更新 directSales（直售皮肤）
[ ] 9. node tools/check.js —— 回归值会变，把新的五个基准值记下来
[ ] 10. 随机抽 2~3 个目标手工核一遍核对表
```

第 9 步要特别注意：**回归断言是按本期数据写死的**。换期后这五个数一定变，需要打开 `tools/check.js` 把期望值改成新的（改之前先确认新值是你手工核过的，否则等于把 bug 固化下来）。

## 数据来源

`meta.source` 里记着公告地址。所有数值都应该能在公告里找到出处；找不到出处的（碎片比例、锦绣档位、券可用率）都在 `params` 或代码注释里标了「未公示 / 默认」。

改数据时请顺手把出处写在 `note` 里，方便下次核对。
